### `2bd30262` (esp32) — "esclavo: fix carrera cap (esperar ARMED antes de sync) + encadenado validado" — 18:03 hs

#### Análisis cuantitativo
| Métrica | Valor |
|---------|-------|
| Archivos modificados | 1 (`slave/src/main.cpp`) |
| Líneas agregadas | ~+90 (incluye watchdog HOT_WAIT completo) |
| Co-autoría | Claude Opus 4.8 |

#### Diff y análisis técnico

El síntoma que motivó este commit era desconcertante: el comando de banco `cap` (captura directa por USB al esclavo, sin pasar por el maestro) funcionaba con tamaños chicos pero fallaba con tamaños grandes — un patrón **no monotónico** que la sesión anterior había atribuido, por error, a "pérdida de frames UART / degradación de hardware". La causa real era mucho más sutil y nada tenía que ver con el hardware degradándose:

```cpp
static void requestCaptureFromUsb(uint16_t n)
{
    requestPrestartFromUsb(n);
    if (g_state == HOT_WAIT) {
        uint32_t deadline = millis() + 800u;
        while (!storeReadyForHotWait() && (int32_t)(millis() - deadline) < 0) {
            psoc.poll();
            servicePsocConfigAck();
            serviceHotWaitWatchdog();
        }
    }
    requestUsbStartFromHotWait();
}
```

Antes del fix, `requestCaptureFromUsb()` llamaba a `requestPrestartFromUsb(n)` y *inmediatamente después* a `requestUsbStartFromHotWait()`, sin esperar a que el PSoC confirmara `PSOC_EVT_ARMED`. Esa confirmación llega de forma asíncrona, típicamente 100-300 ms después del preStart. Si el sync se disparaba antes de que `g_psoc_arm_ready` estuviera en true, el PSoC lo ignoraba (`ready=0`) y la captura se quedaba colgada en `HOT_WAIT` con `fill=0/N` para siempre. La razón de que el síntoma pareciera depender del tamaño era pura casualidad de timing del ACK, no una propiedad real del tamaño de la captura — el path real maestro→esclavo nunca sufría esto porque `PRESTART` y `START` viajan como paquetes separados por radio, con latencia natural entre ellos que enmascaraba el problema.

El fix agrega un busy-wait acotado de 800 ms que sirve activamente `psoc.poll()`, `servicePsocConfigAck()` y el nuevo `serviceHotWaitWatchdog()` hasta que `storeReadyForHotWait()` confirme que el PSoC está listo. El commit también trae consigo — "estaba en working-tree" — un paquete de robustez de `HOT_WAIT` que se había ido acumulando sin commitear: watchdog con re-arm/abort, limpieza de flags viejos al entrar en `ARM`, y bookkeeping del flanco de sync movido del ISR (`onSyncEdge`) al `loop()`:

```cpp
static void IRAM_ATTR onSyncEdge()
{
    ...
        g_sync_edge_started = true; /* loop() completa el bookkeeping fuera del ISR */
        g_state = SAMPLING;
```

Este detalle — sacar trabajo no crítico de una ISR — es una buena práctica de firmware bien aplicada: las interrupciones deben ser lo más cortas posible, y cualquier bookkeeping que no sea estrictamente necesario para el estado inmediato del hardware se pospone al loop principal.

El watchdog nuevo (`serviceHotWaitWatchdog`) resuelve un problema de campo real documentado en el propio comentario del código: *"bug de campo 2026-07-11: START funciona una vez y nunca más"*. Antes de este cambio, si el PSoC nunca confirmaba `ARMED` (por ejemplo porque `sd_session_begin` fallaba silenciosamente y `psoc_arm()` salía sin armar), el esclavo se quedaba mudo hasta un power cycle manual. Ahora reintenta `preStart()` hasta `HOTWAIT_REARM_MAX` (2) veces y, si sigue sin respuesta, aborta limpio con NACK explícito hacia el maestro en lugar de colgar el sistema.

El commit message incluye la validación en banco, con cifras que superan claramente el build de referencia anterior:

```
decim 1 cap 512 -> fill=512/512, fs=2604, 5.90s
decim 2 cap 512 -> fill=512/512, fs=1302, 11.80s (encadenado x2)
decim 3 cap 512 -> fill=512/512, fs=868,  17.70s (encadenado x3)
Supera los 10.59s del build viejo de 1020 Hz.
```

Es decir: no solo se arregló el bug, sino que se demostró que la nueva arquitectura de decimación configurable, encadenando tres capturas consecutivas, sigue siendo más rápida que el build viejo de una sola frecuencia fija de 1020 Hz.

#### Impacto en el proyecto

Este fix es la precondición silenciosa para todo lo que sigue en el día: sin resolver esta carrera, ninguna de las pruebas de banco posteriores (SD, encadenado, aceptación de 10 minutos) habría podido ejecutarse de forma confiable, porque el propio comando de diagnóstico usado para validar el sistema estaba roto.

### `004dbae6` (esp32) — "esclavo: F1 — el watchdog SYNC_STALL destruia capturas SD largas" — 23:51 hs

Este es el commit más importante del día, y posiblemente uno de los más importantes de todo julio: es la caza y corrección, **en vivo durante la propia prueba de aceptación**, del bug que hacía que una captura de 10 minutos terminara con 0 muestras.

#### Análisis cuantitativo
| Métrica | Valor |
|---------|-------|
| Archivos modificados | 1 (`slave/src/main.cpp`) |
| Constantes ajustadas | `PSOC_SD_READ_TIMEOUT_MS`: 250 → 450 ms (hallazgo H3) |
| Co-autoría | Claude Fable 5 |

#### Diff y análisis técnico

El documento `docs/plan_pruebas_precampo.md` (creado en el commit hermano `5bc7223d` del submódulo `docs`) registra la matriz de pruebas completa del día y es la mejor ventana a cómo se descubrió este bug:

| # | Prueba | Resultado |
|---|--------|-----------|
| E1 | RAM chica por radio (`-n 4`) | ✅ PASS 120/120 |
| E2 | SD chica por radio (`-n 600`, 6.9s) | ✅ PASS 18000/18000 |
| E3 | SD mediana por radio (`-n 3000`, 34.6s) | ✅ PASS 90000/90000 |
| E4 | Log paralelo durante E3 | ⚠️ ~3.6% de lecturas SD superan 250ms (H3) |
| E5 | **Aceptación 10 min** (52080 lotes, firmware previo al fix) | ❌ **FAIL — 0 muestras** |
| E5b | Aceptación 10 min con fix F1 | 🔄 en curso al cierre del día |

La causa raíz, tal como quedó documentada tanto en el commit como en el plan de pruebas: el watchdog `VIEW/START_SYNC_STALL` del esclavo estaba diseñado pensando en capturas a RAM, donde `fill`/`bOK` crecen visiblemente durante el muestreo — si esos contadores no se movían en cierto tiempo, el watchdog asumía que el sync se había perdido y reenviaba `START_NOW` al PSoC como fallback de recuperación. Pero en capturas a SD, por diseño, **no llegan lotes UART durante el muestreo** (`fill`/`bOK` quedan congelados intencionalmente), y el cierre del archivo `GEOLAST.BIN` en la SD crece con el tamaño de la captura — unos 3.3 segundos extra para 52080 lotes (~4.7 MB). Con el margen fijo del watchdog (~2.3 s), a los `elapsed=602500 ms` de la captura de 10 minutos el watchdog declaró stall y mandó `START_NOW` al PSoC **955 ms antes** de que llegara el evento `SD_SESSION 0x01` que confirmaba que la captura, en realidad, había terminado *bien* (`fill=52080/52080`). Ese `START_NOW` fantasma re-armó el PSoC, lo que invalidó `GEOLAST.BIN` a mitad de cierre (`SD_ERROR 0x08`), y a partir de ahí cada `REQ_BATCH` del maestro recibía NACK eterno — de ahí las 0 muestras finales, pese a que los datos habían sido adquiridos correctamente.

El propio commit deja constancia de que capturas más chicas (E2 con 600 lotes, E3 con 3000) habían pasado "de casualidad", porque el cierre del archivo SD terminaba antes de que el margen fijo del watchdog se cumpliera: *"toda captura SD larga perdia la carrera siempre"*. Es un ejemplo textbook de un bug de carrera que escala mal con el tamaño de los datos y que por eso puede pasar inadvertido en pruebas cortas.

El fix, en el `loop()` del esclavo:

```cpp
const bool sdCapture = g_psoc_sd_store_active;
if (sdCapture) {
    /* margen extra proporcional al largo: +15s + n/2 ms */
    fallbackMs += 15000u + (uint32_t)(g_rec_n_batches / 2u);
}
if (elapsedMs >= fallbackMs && batchesNow == g_sampling_start_batches_ok) {
    ...
    if (sdCapture) {
        /* NUNCA re-arrancar el PSoC en modo SD */
        digitalWrite(SYNC_TO_PSOC_PIN, LOW);
        g_view_store_active = false;
        g_start_store_active = false;
        g_state = STOPPED;
        sendCfgAck(wasView ? CMD_VIEW : CMD_START, 0);
    } else {
        psoc.startNow();
    }
}
```

Dos cambios independientes trabajando juntos: (1) en modo SD, el margen del fallback ahora escala con el tamaño de la captura (`+15s + n/2 ms`, es decir +41 s extra para las 52080 lotes de la prueba de 10 minutos), dándole tiempo de sobra al cierre del archivo; y (2) si aun con ese margen el watchdog vence, **nunca más se reenvía `START_NOW`** en modo SD — en su lugar se hace un abort limpio (NACK explícito al maestro, línea de sync a LOW, estado `STOPPED`), preservando cualquier dato ya escrito en la SD en lugar de destruirlo con un re-arm.

El mismo commit incluye un segundo ajuste, más chico pero relacionado — el hallazgo **H3** de la matriz de pruebas: durante E4 se había medido que ~3.6% de las lecturas SD por USB (comando `0xBF`) superaban el timeout de 250 ms configurado, generando NACK y reintento evitable del lado del maestro. Se subió a 450 ms para absorber ese pico periódico sin cambiar la lógica de retry.

Un detalle notable del propio código: *"Nota: los prefijos de log del esclavo son `micros()` y dan la vuelta a los 4294.97 s — el 'reboot' aparente en el log era el wrap, no un reset real"* — un recordatorio de que al leer logs de captura de más de ~71 minutos hay que tener presente el overflow de `micros()` en un `uint32_t`, algo que en su momento pudo haber generado una falsa alarma adicional durante el debugging.

#### Impacto en el proyecto

Este es, literalmente, el bug que habría hecho fallar la primera salida de campo con capturas largas a SD — exactamente el escenario que la sesión de auditoría del día estaba tratando de prevenir ("no quiero sorpresas"). El hecho de que se haya reproducido y corregido en vivo, con evidencia capturada (ver el commit siguiente), es el mejor caso posible de por qué vale la pena una sesión de auditoría dedicada antes de ir a terreno.

### Cualitativo

El 11 de julio es, en varios sentidos, el día donde la disciplina de "auditoría antes de campo" paga dividendos concretos. La sesión no fue lineal: arrancó de madrugada con trabajo de interfaz y reconexión automática, tuvo un bache al mediodía ("ayuda dios santo que dificil todo" mientras se acumulaban artifacts de pruebas SD tempranas), encontró alivio a la tarde cuando el usuario resolvió manualmente en la GUI de PSoC Creator el blocker de ruteo analógico que venía bloqueando la variante GEO con SD, y escaló en intensidad hacia la noche cuando la validación de hardware (SD real, encadenado, comando `sdread`) dio paso a la prueba de aceptación de 10 minutos — la que, en teoría, cerraba el ciclo de validación pre-campo.

Que esa prueba fallara con 0 muestras podría haber sido un golpe duro a esa altura de una sesión de ~20 horas. En cambio, se convirtió en el hallazgo más valioso del día: la causa raíz (F1) no era un problema de hardware ni de RF, sino un defecto de diseño puntual y bien delimitado — un watchdog pensado para un modo de captura (RAM) aplicado sin modificación a otro modo (SD) con una dinámica temporal completamente distinta. El propio commit message reconstruye la secuencia de eventos con precisión de milisegundos (`955 ms ANTES` del `SD_SESSION`), lo cual solo es posible gracias a la disciplina de logging que se había ido construyendo en sesiones anteriores. Es un caso de libro de cómo un log bien instrumentado convierte un "0 muestras, no sé por qué" en un diagnóstico preciso y accionable en la misma noche.

Vale la pena notar también el patrón metodológico que se repite con el commit `2bd30262` de la tarde: un bug de comportamiento "no monotónico" (falla con capturas grandes, funciona con chicas) que en una primera pasada se había atribuido erróneamente a degradación de hardware, y que resultó ser una carrera de timing pura. Es la segunda vez en pocas horas que el día expone la misma lección: cuando un síntoma no escala de forma monotónica con el tamaño del problema, es una señal fuerte de que hay una carrera de tiempos de por medio, no una limitación física gradual. Dos bugs del mismo día, dos instancias del mismo patrón de diagnóstico.

El estado del sistema al cierre del día: SD validada en hardware real con encadenado de capturas, comando de banco `sdread` operativo, F1 corregido en el esclavo (con H3 como bonus), y una matriz de pruebas formal (`docs/plan_pruebas_precampo.md`) que deja registro estructurado de qué se probó, qué falló, y qué queda pendiente (E5b, E6-E10) para la continuación al día siguiente. El propio commit del maestro deja explícito que aún falta un paso operativo simple pero necesario — subir el filesystem de la web actualizada a COM8 — antes de que el sistema completo, extremo a extremo, esté en el estado validado. La sesión no cierra con la sensación de "todo listo para campo", sino con la more honesta y más útil: "encontramos el bug que nos iba a arruinar la salida, y sabemos exactamente qué falta para terminar de confirmarlo".
