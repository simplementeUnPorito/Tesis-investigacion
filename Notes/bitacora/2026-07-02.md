**1. `Reg_Select` desaparece; nace el bloque de registros de `superMaquina`.**

El primer indicio en el diff de `main.c` es el cambio de includes:

El viejo `Reg_Select`, un simple registro de control que solo servía para enrutar el DMA (raw vs. filtrado), se reemplaza por un conjunto de cinco Control/Status Registers dedicados (`ctrl`, `cfg`, `reset`, `status`, `error`, `state`) que forman la interfaz completa ARM↔Verilog hacia el nuevo bloque `superMaquina`. Esto no es un simple renombrado: es la superficie de comunicación de una máquina de estados completa que ahora vive en hardware, con su propio ISR unificado (`isr_SuperMaquina`) reemplazando lo que antes eran ISRs separadas de DMA.

El protocolo, documentado en detalle en el handoff del mismo commit, define un mapa de bits denso en `main.c`:

```c
#define CE_CTRL_ARM          0x01u
#define CE_CTRL_START_NOW    0x02u
#define CE_CTRL_STOP         0x04u
#define CE_CTRL_CLEAR_FLAGS  0x08u
#define CE_CTRL_USE_SYNC     0x10u
#define CE_CTRL_LOAD_BATCH_LO 0x20u
#define CE_CTRL_ENGINE_EN    0x40u
#define CE_CTRL_LOAD_BATCH_HI 0x80u

#define CE_CFG_SRC_MASK      0x03u
#define CE_CFG_SRC_RAW       0x00u
#define CE_CFG_SRC_FILTER    0x01u
#define CE_CFG_SRC_COMBINED  0x02u
#define CE_CFG_SRC_DEBUG     0x03u
#define CE_CFG_IRQ_BATCH_EN  0x04u
#define CE_CFG_IRQ_SYNC_EN   0x08u
#define CE_CFG_IRQ_ERROR_EN  0x10u

#define CE_STATUS_IDLE       0x01u
#define CE_STATUS_ARMED      0x02u
#define CE_STATUS_SAMPLING   0x04u
#define CE_STATUS_DONE       0x08u
#define CE_STATUS_ERROR      0x10u
#define CE_STATUS_BUTTON     0x80u
```

Cada bit de `ctrl` es, según el handoff, un *pulso* (se escribe y se vuelve a bajar de inmediato), no un nivel sostenido — salvo `USE_SYNC` y `ENGINE_ENABLE`, que sí son niveles. Este patrón de "pulso vs. nivel" en el mismo registro es exactamente el tipo de contrato que hay que documentar con cuidado, porque un error de un solo bit (dejar un pulso como nivel, o viceversa) puede hacer que la máquina de Verilog quede en un estado inconsistente sin que el C dé ningún error visible.

El helper que empaqueta esta lógica en `main.c`:

```c
static void capture_engine_pulse(uint8 pulse)
{
    ctrl_Write((uint8)(g_ce_ctrl_level | pulse));
    ctrl_Write(g_ce_ctrl_level);
}
```

`g_ce_ctrl_level` guarda el estado de nivel persistente (por ejemplo, si `ENGINE_ENABLE` y `USE_SYNC` están activos), y cualquier pulso se superpone momentáneamente sobre ese nivel base y se retira enseguida — una forma limpia de mantener ambos tipos de señal en el mismo byte de registro sin pisarse.

**2. Cargar el número de lotes (`N`) en Verilog: el truco de guardar `N-1`.**

```c
static void capture_engine_configure_target(void)
{
    uint16 target = capture_target_batches();
    uint16 limit = (uint16)(target - 1u);
    uint8 saved_cfg = g_ce_cfg_level;

    cfg_Write((uint8)(limit & 0xFFu));
    capture_engine_pulse(CE_CTRL_LOAD_BATCH_LO);
    cfg_Write((uint8)((limit >> 8u) & 0x01u));
    capture_engine_pulse(CE_CTRL_LOAD_BATCH_HI);
    cfg_Write(saved_cfg);
}
```

El handoff explica la razón de este truco: "el firmware carga `N-1` para ahorrar lógica de comparador en PLD". En Verilog, comparar un contador incremental contra `N-1` (`==`) es una operación mucho más barata en términos de recursos lógicos (PLD, Programmable Logic Device, dentro del UDB) que compararlo contra `N` con una resta implícita o un comparador de mayor/igual. Es una optimización de bajo nivel típica de FPGA/CPLD que solo tiene sentido una vez que la lógica vive efectivamente en hardware — en software, esta clase de ahorro habría sido irrelevante. El registro `cfg` de 8 bits es demasiado angosto para un valor de 16 bits, así que el firmware lo carga en dos pulsos separados (`LOAD_BATCH_LO`/`LOAD_BATCH_HI`), reutilizando el mismo registro de 8 bits dos veces y restaurando su valor de configuración normal (`saved_cfg`) al final — un patrón de multiplexación temporal de un registro estrecho para transportar un valor más ancho.

**3. Los timers fixed reemplazan el tick de sistema de 10 ms con temporizadores one-shot encadenados.**

Este es, en términos de líneas de código, el cambio más grande del commit dentro de `main.c`. El viejo esquema de un único `Timer` con un tick periódico de 10 ms (`g_timer_ticks`, incrementado en cada interrupción y comparado contra umbrales para saber cuándo hacer ping, parpadear el LED o abortar una calibración) se reemplaza por tres timers fixed independientes, cada uno operado como one-shot reprogramable:

```c
#define TIMER1_MODE_NONE       0u
#define TIMER1_MODE_BOOT_PING  1u
#define TIMER1_MODE_IDLE_PING  2u

#define TIMER2_MODE_NONE          0u
#define TIMER2_MODE_BOOT_LED_OFF  1u
#define TIMER2_MODE_WAIT          2u
#define TIMER2_MODE_COMM_BLINK    3u
```

Como los timers fixed del PSoC son contadores de 16 bits corriendo a 100 kHz (según `TIMER_ILO_COUNTS_PER_MS = 100u`), el rango máximo directo de un solo periodo es de unos 655 ms — insuficiente para, por ejemplo, la ventana de parpadeo de identificación de 8 segundos (`IDENTIFY_BLINK_WINDOW_MS = 8000u`) o el ping idle de 1 segundo. La solución es encadenar "chunks" de a lo sumo `TIMER_MAX_COUNTS` (60.000 cuentas, ~600 ms, dejado con margen bajo el límite físico de 0xFFFF para poder rearmar el one-shot sin desbordar):

```c
static uint16 timer_take_chunk(volatile uint32 *remaining_counts)
{
    uint32 remaining = *remaining_counts;
    uint16 chunk;

    if (remaining == 0u) {
        return 0u;
    }
    if (remaining > TIMER_MAX_COUNTS) {
        chunk = (uint16)TIMER_MAX_COUNTS;
        *remaining_counts = remaining - TIMER_MAX_COUNTS;
    } else {
        chunk = (uint16)remaining;
        *remaining_counts = 0u;
    }
    return chunk;
}
```

Cada vez que un timer dispara su ISR (`isr_Timer_1`, `isr_Timer_2`, `isr_Timer_3`), el handler consume el resto de cuentas pendientes en el próximo chunk hasta agotar el total solicitado — un patrón de "cuenta larga sobre hardware de cuenta corta" que es exactamente lo que hace falta cuando el periférico físico no alcanza para el intervalo deseado en un solo tiro. Esto reemplaza por completo la aritmética de "ticks" (`MS_TO_TICKS`) del esquema anterior por milisegundos reales medidos directamente en cuentas del timer, eliminando una capa entera de redondeo indirecto.

**Timer_3, en particular, se dedica en exclusiva a la calibración asíncrona**, exponiendo una API limpia hacia `calibration.c` a través de `psoc_hw.h`:

**1. Un parser numérico genérico para parámetros de comando USB.**

```c
static bool usbParseU16Param(const char *cmd, const char *word, uint16_t &value)
{
    uint32_t acc = 0;
    if (!usbCommandStartsWithWord(cmd, word)) {
        return false;
    }
    while (*cmd != '\0' && *cmd != ' ' && *cmd != '=' && *cmd != ':') {
        cmd++;
    }
    while (*cmd == ' ' || *cmd == '=' || *cmd == ':') {
        cmd++;
    }
    if (*cmd < '0' || *cmd > '9') {
        return false;
    }
    while (*cmd >= '0' && *cmd <= '9') {
        acc = (acc * 10u) + (uint32_t)(*cmd - '0');
        if (acc > 65535u) {
            return false;
        }
        cmd++;
    }
    while (*cmd == ' ') {
        cmd++;
    }
    if (*cmd != '\0') {
        return false;
    }
    value = (uint16_t)acc;
    return true;
}
```

Antes, `usbParseGainParam` ya existía para parsear valores `uint8` (ganancia PGA), pero acotado a ese caso. Este nuevo parser genérico acepta tres separadores distintos entre el nombre del comando y su valor numérico (espacio, `=`, `:` — por ejemplo `"pre 500"`, `"pre=500"` o `"pre:500"` funcionan igual), valida que el acumulador nunca exceda el rango de un `uint16_t` (chequeo `acc > 65535u` dentro del propio bucle de acumulación, no después — evitando overflow silencioso de `acc` mismo, que es `uint32_t` y podría seguir acumulando dígitos de más sin este corte temprano), y exige que no quede texto basura después del número (salvo espacios finales). Es un parser pequeño pero cuidadosamente defensivo para un canal de entrada no confiable como una terminal serie manual, donde un usuario de laboratorio puede tipear cualquier cosa.

El hecho de que estos breadcrumbs se concentren justo en `psoc_calibration_start_async()` —la función que integra el nuevo `psoc_cal_timer_start` sobre `Timer_3` recién introducido en el commit anterior— sugiere que la calibración era, de los tres subsistemas tocados por `superMaquina`, el que generaba más dudas sobre si el nuevo timer se estaba arrancando y deteniendo correctamente en cada transición de estado.

**2. `Timer_3` queda libre: la lógica de calibración se consolida sobre `Timer` y `Timer_1`.**

El comentario nuevo agregado sobre el mapa de timers en `main.c` es la documentación más clara de la intención de este commit:

```c
+/* Mapa de timers fixed (3 en uso; Timer_3 quedo LIBRE y puede eliminarse del
+ * TopDesign — ver docs/psoc_supermaquina_handoff.md):
+ *   Timer   : watchdog del parser UART RX (concurrente con todo lo demas).
+ *   Timer_1 : ping boot/idle + tick de calibracion (nunca concurrentes:
+ *             la calibracion detiene los pings antes de arrancar).
+ *   Timer_2 : LED/esperas cortas + watchdog de captura (nunca concurrentes:
+ *             la ventana de captura apaga LED/esperas). */

 #define TIMER1_MODE_IDLE_PING  2u
+#define TIMER1_MODE_CAL_TICK   3u
```

Es decir: en el primer commit del día se habían introducido tres timers fixed nuevos (`Timer_1`, `Timer_2`, `Timer_3`), con `Timer_3` dedicado en exclusiva al watchdog/progreso de calibración. En este segundo commit, apenas hora y media más tarde, Elías se da cuenta de que esa dedicación exclusiva era innecesaria: el tick de calibración se puede reutilizar sobre `Timer_1` (agregando un tercer modo, `TIMER1_MODE_CAL_TICK`, junto a los dos que ya tenía para ping de boot/idle), aprovechando que la calibración nunca corre al mismo tiempo que los pings de boot/idle (la calibración los detiene explícitamente antes de arrancar). El resultado neto es que `Timer_3` queda completamente libre y, según la nota, "puede eliminarse del TopDesign" — un bloque de hardware menos para el esquemático de PSoC Creator, que es un recurso físico limitado (solo hay una cantidad finita de UDB/timers fixed disponibles en el chip). Es una optimización de recursos de hardware hecha *después* de constatar, en la misma madrugada, que el diseño inicial de "un timer por subsistema" era más generoso de lo necesario.

**3. El buffer de captura se aplana: de una matriz de lotes a un puntero corriendo.**

```c
-static volatile uint8  g_capture_raw[PSOC_CAPTURE_MAX_BATCHES][CAPTURE_BATCH_BYTES];
-static volatile uint16 g_batch_fill       = 0u;
-static volatile uint8  g_batch_ready      = 0u;
+static volatile uint8  g_capture_raw[(uint32)PSOC_CAPTURE_MAX_BATCHES * CAPTURE_BATCH_BYTES];
+static volatile uint8 * volatile g_capture_wr  = g_capture_raw;
+static volatile uint8 * volatile g_capture_end = g_capture_raw;
```

El comentario que acompaña el cambio explica la motivación: "El hot path de la ISR solo copia 3 bytes al puntero de escritura; el alineado de counts se difiere al volcado UART". Antes, el buffer era una matriz bidimensional indexada por lote y posición dentro del lote, lo cual implica que cada escritura desde la ISR tenía que calcular un offset de dos dimensiones (`g_capture_raw[batch_index][byte_index]`). El nuevo esquema lo aplana a un arreglo unidimensional con un puntero de escritura (`g_capture_wr`) que simplemente avanza 3 bytes por muestra, sin ningún cálculo de índice — el patrón típico de optimización de hot path de ISR, donde cada ciclo de reloj cuenta y evitar una multiplicación/desplazamiento por cada muestra (a una tasa de miles de muestras por segundo) es una ganancia de tiempo real medible. La conversión de vuelta a un formato con separación por lotes/alineado de escala (`DEC_DIV`) se pospone al momento del volcado por UART, que corre a una cadencia mucho más relajada y donde el costo de ese cálculo ya no es crítico.


Este comentario formaliza en el propio código C una advertencia que ya estaba en el handoff del commit anterior: la constante `FILTER_GROUP_DELAY` (63 muestras, calculada como `(FILTER_FIR_NTAPS - 1) / 2`) tiene ahora una contraparte espejada dentro del propio archivo Verilog `superMaquina.v` (`FIR_DISCARD_SAMPLES`), y ambas tienen que mantenerse sincronizadas manualmente si el filtro FIR cambia de longitud en el futuro. Es exactamente el tipo de acoplamiento entre dos lenguajes distintos (C y Verilog) que, sin un comentario explícito como este en ambos lados, es fácil de romper silenciosamente meses después cuando alguien cambia un solo lado del par.
