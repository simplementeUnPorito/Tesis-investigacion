#### Diff y análisis técnico

Lo primero que hay que aclarar es que este commit no es "un" cambio: es la fusión de al menos tres decisiones de diseño distintas, cada una documentada en su propio archivo de auditoría dentro de `server/audits/`, más una reescritura sustancial del gate de pruebas.

**1. De "Borrado" a cuarentena reversible.** El cambio más importante en términos de contrato con el usuario está en `server/deletion.py`. El docstring del módulo lo dice explícito:

```python
-"""Borrado con banderas y subgrupos (PORT_PLAN §4).
+"""Cuarentena reversible con banderas y subgrupos (PORT_PLAN §4).

-Reemplaza los dos botones sueltos: una tabla de carpetas con banderas
-combinables, subgrupos por sitio y por distancia, selección múltiple y una
-confirmación que **lista** lo que va a borrar.
+El tab conserva el nombre histórico «Borrado», pero ninguna ruta elimina
+archivos. Las carpetas seleccionadas reciben la bandera compartida
+``frd.GLOBAL_DISABLED_LABEL`` en ``alignment_disabled_folders.json``. Así
+quedan fuera del pipeline científico y pueden restaurarse sin perder raw, ZIP,
+anotaciones ni procedencia.
```

Según `IMPLEMENTATION_AUDIT.md`, esta es una decisión tomada el 26 de julio: "El usuario reemplazó expresamente el requisito original de Borrado: ninguna carpeta, captura ni ZIP debe eliminarse." La implementación usa una clave reservada `GLOBAL_DISABLED_LABEL` (`__all__`) dentro del JSON compartido `alignment_disabled_folders.json` — el mismo archivo que PyQt ya usaba para rechazos por grupo (`::grupoN`), así que la web no inventa un formato paralelo, extiende uno existente. `Pipeline.delete_folder()` queda "clausurado" (según el audit) y devuelve un error seguro; ya no contiene `rmtree` ni borrado de ZIP. Las rutas viejas (`/api/deletion/delete`, `/api/delete`, `/api/delete-sin-hammer`) se mantienen por compatibilidad hacia atrás con clientes existentes, pero ahora sólo aplican la bandera reversible — nunca tocan disco.

Esta decisión tiene una motivación de seguridad de datos bastante concreta para un proyecto de tesis con captura de campo cara de repetir: una operación de "borrado" hecha por error (click equivocado, filtro mal aplicado, confirmación apresurada) ya no puede destruir una campaña. Se cambia irreversibilidad por reversibilidad, al costo de un poco más de estado a mantener (`alignment_disabled_folders.json` con locks entre procesos, según el audit, porque PyQt y la web pueden escribir el mismo archivo concurrentemente).

**2. `AnalysisJobs`: una segunda cola de trabajos, científica y persistente.** `server/analysis_jobs.py` es un módulo enteramente nuevo (+272 líneas) que separa la cola de *ingesta* (`Pipeline`, que ya existía) de una cola de *cómputo científico* (dispersión, inversión MASW). Según el audit: "un único proceso científico hijo activo y cancelable", con progreso, aislamiento y recuperación tras reinicio. Esto resuelve un problema práctico de la inversión MASW: son procesos largos (evodcinv+disba, Monte Carlo, MASWavesPy, ADsurf, Geopsy) que no se pueden ejecutar en el hilo de una request HTTP sin bloquear el servidor, y que el usuario necesita poder cancelar si eligió mal los parámetros.

**3. `masw.py` (+622 líneas) y `masw.js` (+660 líneas): el módulo más grande del porteo.** Es la pieza central del pipeline científico — dispersión, combinación ponderada de grupos, normalización por frecuencia, edición de picks por arrastre, múltiples backends de inversión. El audit documenta que "el mejor modelo original queda inmutable en NPZ; `edited_profile` es una copia editable por capas" — otra instancia del mismo patrón de diseño defensivo que aparece en `deletion.py`: nunca destruir el dato original, sólo agregar una capa editable encima.

**4. `smoke_test.py` crece a +2120 líneas.** Es, con mucha diferencia, el archivo más grande del commit. El audit dice explícitamente: "manifiesto explícito de 58 checks obligatorios para impedir verdes falsos" y reporta el resultado real de la última corrida:


Esto es un gate de regresión end-to-end cubriendo: validación de estructura de ZIP v4, límites de subida/expansión, protección contra ZIP bomb y path traversal, CRC y deduplicación por SHA-256, filtro DC/línea 50-60Hz con armónicos, conflictos de revisión optimista (409), y — a juzgar por los nombres de los audits — remediación de hallazgos de una revisión adversarial externa (`20260727_fable_adversarial_remediation.md`). El hecho de que el número exacto de checks (58) se documente tanto en el audit como implícitamente en el propio script sugiere que el criterio de "terminado" para este porteo no es subjetivo, sino un contrato verificable.

Es la base sobre la que se apoyan tanto `deletion.py` como el resto de los routers que ahora devuelven `409` ante conflictos — necesario porque PyQt y la web pueden estar escribiendo el mismo JSON compartido al mismo tiempo, un problema que no existía cuando sólo había una app de escritorio con un único usuario.

El audit es honesto sobre el estado de esto: "No había Docker, Podman ni nerdctl en el host, por lo que la imagen y compose se validaron estructuralmente, pero el build, healthcheck y reinicio dentro de un contenedor siguen pendientes de ejecutar en una máquina con engine." #### Impacto en el proyecto

Este commit mueve el `PORT_PLAN` de "arrancado" a "con paridad funcional cubierta por un gate automatizado de 58 checks" en las áreas más riesgosas: ingesta, filtros, borrado/cuarentena, MASW y concurrencia multi-cliente. Para una tesis que depende de campañas de campo costosas de repetir (geófonos SM-24, salidas físicas con el hammer), es una decisión de gestión de riesgo más que de ingeniería de software pura.
