#### Diff y análisis técnico

Este es el primer bug encontrado del día, y es directamente el continuador de la prueba E5b que había quedado congelada al 93.2% la noche anterior. El diagnóstico, tal como lo describe el commit, es preciso: un drop de WiFi sin el cierre limpio del socket (sin paquete `FIN`) deja al cliente Python en un estado "medio-muerto" — el socket sigue "vivo" desde la perspectiva del sistema operativo, pero nunca más va a recibir datos. La función `poll_once()` interpretaba esto como un timeout limpio y silencioso, y el runner de captura simplemente esperaba pacientemente el `dump_timeout` completo, que a la escala de la prueba E5b (52.080 lotes) equivale a **46 minutos** de espera inútil.

Mientras tanto, del otro lado, el maestro (ESP32) había pausado el dump precisamente porque detectó que no había cliente activo — un mecanismo de seguridad correcto en el maestro que, combinado con el bug del lado cliente, generaba un deadlock efectivo: el maestro esperando que el cliente reconecte, el cliente esperando pacientemente datos que nunca van a llegar porque el maestro está pausado.

El fix agrega un watchdog de silencio específico para la fase de dump:

```python
# Watchdog de silencio (F5, 2026-07-12): un socket medio-muerto
# (WiFi drop sin FIN) hace que poll_once devuelva timeout limpio
# para siempre y el tool esperaba TODO el dump_timeout (46 min a
# 52080 lotes) sin reconectar, mientras el maestro pausaba el dump
# por falta de cliente. Si estamos en fase dump y no llega DATA
# por >20 s, tirar el socket: ensure_connected re-hace el takeover
# y el maestro reanuda el dump donde quedó.
if (self.first_data_at is not None
        and self.last_data_at is not None
        and self.sock is not None
        and self.samples_written < self.expected_samples
        and time.monotonic() - self.last_data_at > 20.0):
    self.last_data_at = time.monotonic()
    self._drop_socket("sin DATA >20s durante dump; forzando reconexion")
```

La lógica es cautelosa: solo actúa si ya se recibió al menos un dato (`first_data_at is not None`, para no interferir con el arranque normal de la conexión), si hay un socket activo, y si todavía faltan muestras por escribir. El umbral de 20 segundos es una decisión de ingeniería razonable — suficientemente corto para no perder mucho tiempo en un dump de 46 minutos, suficientemente largo para no gatillar falsos positivos por jitter normal de red. Al forzar el drop del socket, el mecanismo existente de `ensure_connected()` entra en acción y re-hace el "takeover" WebSocket, permitiendo que el maestro reanude el dump exactamente donde había quedado.

#### Impacto en el proyecto

Este fix es la diferencia entre una prueba de aceptación de campo que puede colgarse indefinidamente sin explicación clara, y una que se auto-recupera. Para un sistema pensado para operar en campo con conectividad WiFi inherentemente inestable (geófonos distribuidos, posible interferencia, distancias variables), la resiliencia del cliente de captura ante drops de conexión no es un detalle cosmético — es una condición de uso real.

### `2c07067` (esp32) / `3e41a0b` (docs) — "fix(F9): START rompia el nodo — race PRESTART retry vs PSoC ARMED silencioso" — 19:08 hs

#### Análisis cuantitativo
| Métrica | Valor |
|---------|-------|
| Archivos modificados (esp32) | 4 |
| Líneas agregadas | +349 |
| Líneas borradas | -3 |
| Submódulo | `src/firmware/esp32` (maestro y esclavo) |

#### Diff y análisis técnico

Este es, junto con F5, el hallazgo técnico más importante del día — y probablemente de toda la semana de auditoría pre-campo. El commit message reconstruye la causa raíz con el mismo nivel de precisión que ya se había visto en el F1 del día anterior:

El flujo `VER` (solo verificar, sin armar captura) siempre había funcionado bien. El flujo `START` normal, en cambio, **rompía el nodo siempre**, forzando un reset físico. La causa: el retry del estado `HOT_WAIT` en el maestro, al vencer su timeout de consulta (120 ms), no solo re-consultaba el estado del esclavo sino que **también volvía a emitir `broadcastPrestart()`**. El problema es que el PSoC real tarda ~130 ms en confirmar el evento `PSOC_EVT_ARMED` — es decir, **10 ms más que el timeout del maestro**. En la inmensa mayoría de los casos, el primer retry del maestro llega justo cuando el PSoC ya está armado pero el esclavo todavía no se enteró, y el `broadcastPrestart` redundante fuerza al esclavo a reenviar el comando `SETN` a un PSoC que, por diseño, **deja de escuchar UART por completo** una vez que entra en `PSOC_ARMED` (es la ventana de muestreo silenciosa, necesaria para no perder ciclos de ADC). El `SETN` nunca se ackea, vence a los 500 ms, y el esclavo — pensando que algo salió mal — libera el store y pasa a `STOPPED`, mientras el PSoC queda físicamente armado y sordo, sin nadie que le vuelva a mandar el `SYNC` que espera. Resultado: nodo roto, sin salida posible salvo un reset físico.

`VER` nunca mostró el bug porque su propio retry solo re-consulta, sin volver a armar nada.

El fix, en dos capas, con un comentario extenso justo en el punto de la corrección — señal de que el propio autor sabe que esta línea es la clave de todo el bug y no quiere que nadie (ni su yo futuro) la vuelva a tocar sin entender por qué:

```cpp
// master/src/main.cpp
if (g_hotWaitRetries < HOTWAIT_QUERY_RETRIES) {
    g_hotWaitRetries++;
    /* Solo re-consultar, NUNCA re-broadcastear PRESTART aca: el
     * esclavo puede ya estar HOT_WAIT/armado (el PSoC real tarda
     * ~130 ms en confirmar EVT_ARMED, mas que este timeout de
     * 120 ms, asi que el primer query casi siempre le gana de
     * mano). Un broadcastPrestart redundante fuerza al esclavo a
     * reenviar SETN a un PSoC que ya entro en silencio UART total
     * en PSOC_ARMED -> SETN nunca ackea -> el esclavo aborta,
     * libera el store y el PSoC queda armado y sordo para
     * siempre (roto hasta reset fisico). VER nunca tuvo este bug
     * porque su retry (mas abajo) tampoco re-arma. */
    sendHotWaitQuery(g_hotWaitQueryNode);
    ...
```

Y en el esclavo, se añade idempotencia a `CMD_PRESTART`:

```cpp
// slave/src/main.cpp
if (g_state == HOT_WAIT && requested == g_rec_n_batches &&
        storeReadyForHotWait()) {
    /* PRESTART duplicado/redundante (retry del maestro, reenvio ESP-NOW):
     * este nodo ya esta armado y listo para el mismo N. Responder el ACK
     * directo en vez de repetir enterHotWait(): ... */
    sendHotWaitAck();
    ...
} else {
    enterHotWait(msg->n_batches);
}
```

Es una solución "en capas" — no solo se evita la causa raíz en el maestro (no reemitir PRESTART en el retry), sino que además se blinda al esclavo para que, ante cualquier PRESTART duplicado que igual llegue (por ejemplo por un reenvío de ESP-NOW a nivel de radio, fuera del control del maestro), responda de forma idempotente en vez de repetir el armado. Es defensa en profundidad ante una clase entera de bugs de "comando duplicado", no solo ante el caso puntual encontrado.

La validación es exhaustiva y en hardware real: tras reflash + `ToggleReset` + auto-calibración, se corrieron 261 lotes en modo RAM y 600 lotes en modo SD encadenado, ambos PASS con **0 casos** de `SETN_TIMEOUT` o `HOT_WAIT_ABORT`; 3 repeticiones extra, 3/3 PASS; y se verificó que `VER` sigue sin regresión. Se deja además un runner persistente, `start_flow_regression_test.py` (280 líneas), para que este bug —de los más graves encontrados en toda la auditoría— nunca vuelva a colarse sin ser detectado automáticamente.

#### Impacto en el proyecto

F9 es, junto con F1 del día anterior, de los bugs más serios de toda la campaña de auditoría pre-campo: rompía el caso de uso más básico del sistema (arrancar una captura) de forma reproducible al 100%. De haberse ido a campo sin este fix, cada geófono habría requerido un reset físico manual tras cada intento de `START` — inviable en una campaña real con múltiples nodos distribuidos en terreno. El nivel de detalle del diagnóstico (diferencia de 10 ms entre un timeout de 120 ms y una latencia real de 130 ms) es un ejemplo del tipo de bug que solo aparece con hardware real bajo condiciones reales, y que ningún test unitario o simulación hubiera podido predecir sin ese conocimiento empírico previo del comportamiento temporal exacto del PSoC.

Es una regeneración completa de la tabla de coeficientes (formato Q1.23, 4 bytes por tap, little-endian — el formato nativo del componente `Filter` de PSoC), acompañada de una nota-recordatorio para el propio autor sobre un detalle sintáctico traicionero del macro en C (la continuación de línea con `\` es obligatoria incluso en líneas con comentarios, algo que de romperse produce errores de compilación confusos). ### Cualitativo

El 12 de julio es la culminación de la campaña de auditoría pre-campo iniciada el día anterior, y probablemente el día de mayor densidad de hallazgos críticos de toda esa campaña. La estructura del día tiene una simetría casi narrativa: arranca resolviendo el problema que había dejado pendiente el 11 (F5, el dump que se cuelga por un socket zombie), avanza metódicamente por una matriz de pruebas cada vez más amplia (E6 a E18), llega a un pico de confianza a media tarde con el veredicto formal de "listo para campo" — y entonces, como suele pasar cuando se prueba el sistema más allá de los runners automatizados, aparece el bug más serio de todos: START rompe el nodo, siempre, sin excepción.

Lo que distingue a F9 de otros bugs documentados en la bitácora es la precisión quirúrgica del diagnóstico: una diferencia de apenas 10 milisegundos entre un timeout de consulta (120 ms) y la latencia real de un evento de hardware (~130 ms) alcanza para producir un fallo total y determinístico del sistema. Es el tipo de bug que no se encuentra leyendo código ni con tests unitarios — solo aparece midiendo con precisión el comportamiento temporal real del PSoC bajo condiciones reales, y solo se explica una vez que se entiende a fondo por qué el PSoC deja de escuchar UART al entrar en modo armado. El hecho de que el fix venga acompañado de una segunda capa de defensa (idempotencia del comando `CMD_PRESTART` en el esclavo) revela una maduración metodológica: no alcanza con arreglar la causa raíz puntual, hay que preguntarse qué otra clase de eventos podría disparar el mismo patrón de falla (reenvíos de ESP-NOW a nivel de radio, por ejemplo) y blindar contra esa clase completa, no solo contra la instancia observada.

El cierre del día con trabajo sobre el filtro FIR del PSoC, y el tono explícitamente agotado de los mensajes ("Ya se acaba el dolor", "el dolor nunca acaba"), deja constancia de que esta fue una sesión larga y demandante — casi 22 horas de trabajo activo repartidas en dos bloques, con dos bugs de campo genuinamente serios encontrados y corregidos en el mismo día, además de una batería completa de pruebas de regresión nuevas que quedan como activo permanente del proyecto (`start_flow_regression_test.py`, `sd_max_regression_test.py`, `usb_regression_test.py`, `ws_fault_test.py`, entre otras). Al cierre del día, el sistema del banco queda, esta vez sí, con el flujo START validado en hardware real con cero fallos en múltiples repeticiones — la condición que faltaba para sostener con confianza el veredicto de "listo para campo" que se había declarado (prematuramente) unas horas antes.
